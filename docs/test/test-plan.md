# 测试计划与用例

## 1. 文档信息

| 项目 | 内容 |
|---|---|
| 负责人 | `ChatGPT@root` |
| 对应任务 | T-03 测试、质量门禁与验收 |
| 当前阶段 | P0 工程与契约 |
| 需求基线 | 需求规格说明书 0.1.1 |
| 测试范围 | P0.1～P0.3；后续阶段按门禁逐轮补充 |
| 状态 | P0 测试基础 |

## 2. 目标与原则

- 用可重复的原始证据验证 P0 工程、健康检查、统一错误契约和客户端启动门禁。
- 测试只验证交付是否符合已确认契约，不代替 T-01、T-02 修改实现。
- 正式门禁只在 T-01、T-02 都标记“待测试”并冻结后执行。
- 失败必须保留完整输出，定位到冻结提交、环境、模块和场景。
- 任何测试通过结论都必须由 `root` 记录，并由项目组长复核后解锁下一阶段。

## 3. 测试环境与数据

| 项目 | 约定 |
|---|---|
| 操作系统 | Windows 11 |
| Node.js | `>=24.18.0` |
| pnpm | `11.21.0` |
| API 地址 | `http://127.0.0.1:3000/api/v1` |
| 桌面端 | Electron + React，按 `pnpm dev:desktop` 启动 |
| 数据库 | 本地 SQLite `data/app.db` |
| 测试数据 | 使用确定性种子或隔离临时数据；不得提交数据库、日志和真实凭据 |
| 冻结版本 | 记录 `git rev-parse HEAD` 和任务 PR |

## 4. 命名与目录

- 测试编号：`P0-<区域>-<三位序号>`，例如 `P0-API-001`。
- 跨模块测试：`tests/p0/`、`tests/p1/` 等按阶段分目录。
- 单项测试：`<范围>.test.ts`。
- 检查脚本：`check-<场景>.mjs`。
- 证据：使用 `docs/test/p0-evidence-template.md`，每轮门禁单独填写。

## 5. 测试层次

| 层次 | 目的 | P0 工具 |
|---|---|---|
| 环境检查 | 确认 Node、pnpm、分支和提交可追踪 | `pnpm test:p0-env` |
| API 契约 | 验证健康检查和统一错误响应 | `pnpm test:p0-smoke` |
| 工程质量 | 验证格式、类型、构建和已有测试 | `pnpm lint`、`pnpm typecheck`、`pnpm test`、`pnpm build` |
| 数据库 | 验证 Migration 可重复执行及默认路径 | `pnpm db:migrate` |
| 桌面端 | 验证启动、未登录拦截和请求失败不崩溃 | 手工步骤、截图或录屏，后续补充自动化 |

## 7. 执行命令

```powershell
pnpm test:p0-env

# 在 API 已启动的另一个终端执行
pnpm test:p0-smoke

pnpm db:migrate
pnpm lint
pnpm typecheck
pnpm test
pnpm build
```

桌面端手工检查：

```powershell
pnpm dev:desktop
```

## 8. 进入与退出条件

进入正式门禁：

- T-01、T-02 均已标记“待测试”并进入全员冻结。
- 两个任务的交付 PR、冻结提交、测试结果和交接信息可追溯。
- 测试环境完成依赖安装和本地 `.env` 配置。

退出正式门禁：

- P0 适用用例全部通过，或失败项已记录 Issue 并明确责任任务。
- 原始命令和输出完整，安全检查未发现敏感信息泄露。
- `root` 记录阶段结论，项目组长复核确认后才能解锁 P1。

## 9. 缺陷与阻塞

- P0 阻断问题使用 GitHub Issue，类型 `bug` 或 `blocker`，关联 T-01、T-02 或 T-03。
- 测试阻塞不得通过修改业务实现、删除测试或降低断言来绕过。
- 发现跨任务契约冲突时保持冻结，由 `root` 裁决后再指定修复范围。

## 10. 证据模板

每轮执行使用 [P0 证据模板](p0-evidence-template.md)，原始输出优先保存为文本文件；截图或录屏用于桌面端界面证据。
