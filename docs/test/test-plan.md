## 2. 目标与原则

- 用可重复的原始证据验证当前阶段的需求与契约。第 3～10 节保留 P0 历史用例和执行说明；当前 P7 范围、判据和待执行清单以第 11 节及 T-03 为准。
- 测试只验证交付是否符合已确认契约，不代替 T-01、T-02 修改实现。
- 正式门禁只在 T-01、T-02 都标记“待测试”并冻结后执行。
- 失败必须保留完整输出，定位到冻结提交、环境、模块和场景。
- 任何测试通过结论都必须由 `root` 记录，并由项目组长复核后解锁下一阶段。

## 4. 命名与目录

- 测试编号：`P0-<区域>-<三位序号>`，例如 `P0-API-001`。
- 跨模块测试：`tests/p0/`、`tests/p1/` 等按阶段分目录。
- 单项测试：`<范围>.test.ts`。
- 检查脚本：`check-<场景>.mjs`。
- 证据：使用 `docs/test/p0-evidence-template.md`，每轮门禁单独填写。

## 8. 进入与退出条件

进入正式门禁：

- T-01、T-02 均已标记“待测试”并进入全员冻结。
- 两个任务的交付 PR、冻结提交、测试结果和交接信息可追溯。
- 测试环境完成依赖安装和本地 `.env` 配置。

退出正式门禁：

- P0 适用用例全部通过，或失败项已记录 Issue 并明确责任任务。
- 原始命令和输出完整，安全检查未发现敏感信息泄露。
- `root` 记录阶段结论，项目组长复核确认后才能解锁 P1。

## 9. 缺陷与阻塞

- P0 阻断问题使用 GitHub Issue，类型 `bug` 或 `blocker`，关联 T-01、T-02 或 T-03。
- 测试阻塞不得通过修改业务实现、删除测试或降低断言来绕过。
- 发现跨任务契约冲突时保持冻结，由 `root` 裁决后再指定修复范围。
