## 问题一：加入迭代成功但响应丢失

`ensureIterationTaskAssigned` 在重试前先调用目标迭代详情，用任务 ID 判断是否已经加入。若已加入，直接标记为完成，不再发送加入请求；若 POST 返回 `ITERATION_TASK_MOVED` 409，则再次读取目标迭代，确认任务已在目标迭代后才恢复成功。

真实 Electron 故障注入流程：

1. 拦截整改任务的加入迭代 POST，先转发到真实 API，再向页面返回错误响应。
2. 页面显示“整改任务已创建，但加入迭代失败”。
3. 点击重试，网络记录显示为 `GET /projects/:id/iterations/:iterationId`，没有第二次 POST。
4. 整改任务链接和验收详情刷新成功，同名任务数量为 1。

该顺序验证了“服务端已成功、响应丢失”的恢复路径，而不是仅模拟请求从未到达服务端。

## 问题二：创建期间切换验收记录

验收创建、保存、整改任务提交和记录切换共用同一互斥状态；提交期间列表记录全部禁用，`selectAcceptance` 入口也会拒绝过期切换。创建响应只在最初选中的验收记录仍有效时更新当前详情和提示。

真实验证创建请求延迟 900 ms，在“正在创建...”期间检查已有验收记录按钮为 disabled，创建完成后新记录正常显示。

## 问题三：清空验收日期

真实 API 探测结果：

```json
{"name":"null","status":400,"error":{"code":"VALIDATION_FAILED","details":["acceptanceDate must be a valid ISO 8601 date string"]}}
{"name":"empty-string","status":400,"error":{"code":"VALIDATION_FAILED","details":["acceptanceDate must be a valid ISO 8601 date string"]}}
```

当前 `UpdateAcceptanceDto` 只允许合法的 ISO 日期字符串，无法通过 `null` 或空字符串清除日期。前端因此：

- 检测编辑表单从已有日期变为空值；
- 阻止提交并在日期字段显示“当前后端暂不支持清除验收日期，请重新选择日期或保留原日期。”；
- 不再出现“保存成功但旧日期仍在”的误导状态。

真正清除日期需要 T-01 明确支持 `acceptanceDate: null`、在 service/DTO 中持久化为 `null` 并补充 API 测试；前端在本轮不修改后端契约。
