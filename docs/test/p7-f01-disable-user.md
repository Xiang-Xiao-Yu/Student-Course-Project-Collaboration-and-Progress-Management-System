# P7-F01 禁用用户修复与复测

依据 FR-01 既有“禁用用户”要求，补齐管理员实际操作入口。原始最终验收记录见 [P7 报告](p7-final-2026-11-12.md)，其中的未通过结论保留为修复前证据。

## 实现方案

- API：`GET /api/v1/users/admin` 返回用户 id、用户名、昵称、状态、管理员标记和更新时间；`POST /api/v1/users/:userId/disable` 接收 `confirmUsername`。仅 ACTIVE 平台管理员可操作，权限在服务端校验。
- 管理员账号受保护；普通用户的禁用需再次确认。无效/不存在对象、用户名不匹配、无权限和网络失败均有明确提示；重复禁用不重复审计或递增会话版本。
- 事务内重新校验管理员，设置 DISABLED 并递增 tokenVersion，旧令牌立即失效。业务数据与成员关系保留。
- 新增 UserDisableAudit 存储操作者、目标、原状态、新状态和时间，不记录密码或令牌；迁移仅新增审计表和索引，无旧数据变换。使用独立审计是因为 ActivityLog 强制绑定项目，而平台用户可能不属于任何项目。
- UI：账户区增加管理员可见的用户管理入口，列表显示状态、角色和禁用按钮；禁用前显示确认对话框；请求期间禁用冲突操作，失败保留原列表和可重试入口。非管理员直达路径也不能取得列表或写入。

## 执行顺序

1. 新增真实 HTTP/SQLite 测试，确认缺失接口导致预期失败。
2. 实现迁移、API、页面和最小导航；补充 UI/API 单元检查。
3. 正常、越权、管理员保护、幂等、事务回滚与并发检查。
4. 真实标准 Electron 操作和已登录被禁用用户验证；更新 P7 复测结论。

## 验收判据

管理员可通过系统禁用普通账号；非管理员不能读取管理列表或禁用其他人；管理员账号不可禁用；禁用后旧令牌及新登录被拒绝；审计与状态原子提交，重复请求不制造重复记录，失败不误报成功；现有注册、登录、资料、头像、项目和历史数据行为不回归。

### 关键行为

- 入口：管理员登录后从项目中心或账户导航进入“用户管理”；选择普通用户，确认禁用。
- 会话：禁用在事务中递增 tokenVersion，既有会话下一次受保护请求返回401并退出；禁用提交后的登录返回403。
- 登录若在禁用前已开始，可能返回旧版本令牌，但该令牌不能访问受保护数据；不能将该交错场景表述为一律登录403。
- 管理员本人及其他管理员均受保护；重复禁用仅保留一条审计，状态已为DISABLED时不重复递增会话版本。
- 列表和异步通知按账号隔离；已确认延迟的管理员200响应在退出并登录普通用户后不显示旧列表。
- 只设置用户状态，不移除成员、改动任务或删除历史；失败的审计写入会连同状态和会话版本一起回滚。
