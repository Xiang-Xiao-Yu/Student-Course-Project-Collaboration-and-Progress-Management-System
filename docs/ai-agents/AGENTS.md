# 其他智能体工作规范

## 仓库定位

- GitHub 仓库：https://github.com/Xiang-Xiao-Yu/Student-Course-Project-Collaboration-and-Progress-Management-System
- GitHub Issues：https://github.com/Xiang-Xiao-Yu/Student-Course-Project-Collaboration-and-Progress-Management-System/issues
- GitHub Pull Requests：https://github.com/Xiang-Xiao-Yu/Student-Course-Project-Collaboration-and-Progress-Management-System/pulls
- 创建 Issue 或提交 PR 前，先确认目标仓库为上述地址；未获授权不得操作其他仓库。

## 1. 适用对象与优先级

- 本文件适用于本项目中除 `root` 外的所有智能体，包括前端、后端、测试、文档、评审和临时智能体。
- 其他智能体开始任何任务前，必须先阅读根目录 `AGENTS.md`、本文件、`docs/需求规格说明书.md` 以及自己的任务说明。
- 项目组长是项目级决策者，`root` 是唯一的主智能体和智能体工作协调者。其他智能体必须接受 `root` 的任务分配、范围限制、接口约定、优先级调整和停止指令。
- 发生规则冲突时立即停止相关操作并报告 `root`，不得自行解释为扩大权限。

## 2. 授权范围

- 只处理 `root` 明确分配的任务、FR/AC、目录和文件。未列入任务范围的内容默认无修改权限。
- 可以读取完成任务所需的项目文件，但不得借排查、重构或顺手修复之名修改任务范围外的代码、文档、配置或数据。
- 发现范围外问题时，只记录文件位置、现象、影响和建议，交由 `root` 决定是否另行立项。
- 不得向其他智能体分派任务、改变公共接口、替其他智能体作出承诺，或自行宣布需求、里程碑和项目已完成。

## 3. 严格只读文件

以下文件和目录对其他智能体严格只读，只能由 `root` 修改：

- 根目录 `AGENTS.md`；
- `docs/ai-agents/AGENTS.md`；
- `docs/需求规格说明书.md`；
- `docs/P0-工程与契约约定.md`；
- `docs/ai-logs/README.md` 和其他智能体的日志文件夹；
- 其他智能体的 `docs/ai-logs/<agent-id>/YYYY-MM-DD.md`；
- `.git/` 内的全部内容及仓库历史；
- 依赖清单和锁文件，包括 `package.json`、各工作区的 `package.json`、`package-lock.json`、`pnpm-lock.yaml`、`yarn.lock`；
- Prisma Schema、已有 Migration、种子数据和实际数据库文件；
- 身份认证、授权、密钥、Token、上传安全、CI、发布和部署配置；
- `root` 在任务说明中追加标记为只读的文件或目录。

如果任务需要调整上述内容，其他智能体只能提交变更建议、影响分析和建议补丁说明，不得直接编辑、覆盖、删除、移动或重命名。

受保护文件在 Windows 上由 root 设置为只读和隐藏。其他智能体即使具备本地文件系统权限，也不得尝试解除属性或绕过 Git、文件系统和 root 审核规则。只有 `ChatGPT@root` 在项目组长明确要求或批准的监督范围内，才能临时解除属性修改；修改后必须恢复只读和隐藏属性，并在 root 日志中记录。

`docs/tasks/` 下的任务文档不属于 root-only 文件。任务负责人可以修改自己任务文档中的“进度记录”“验证记录”和“交接记录”，并通过自己的分支和 PR 交付；不得修改其他任务文档，也不得修改任务范围、验收标准、依赖、文件权限和阶段顺序。root 负责最终审核、协调和必要的监督修改。

## 4. 文件修改规则

- 只修改 `root` 指定的文件；新增文件也必须位于获准目录，并服务于指定 FR/AC。
- 修改前检查真实目录、未提交改动和相关实现，保留现有内容，不覆盖用户或其他智能体的工作。
- 使用补丁方式编辑；禁止批量替换、递归移动、递归删除、强制覆盖和未经检查的自动格式化。
- 不得修改公共 API、共享类型、数据库结构、权限模型或跨模块约定。确有需要时先向 `root` 提交影响分析并等待新指令。
- 不得新增、升级或移除依赖，不得更换技术栈、构建工具、包管理器或目录结构。

## 5. Git、分支与 Pull Request

- 禁止直接在 `main` 或 `master` 上提交，禁止直接推送受保护分支。
- 每项任务使用 `root` 指定的功能分支或独立 worktree；未指定时先报告，不得自行占用他人的分支。
- 分支名使用 `feat/`、`fix/`、`docs/`、`test/`、`refactor/` 或 `chore/` 前缀。
- 所有代码和文档交付必须通过 Pull Request，不得绕过 PR 合并，不得把未评审内容直接并入目标分支。
- 只有在 `root` 明确授权时才能执行 `git commit`、`git push`、创建或更新 PR；禁止强制推送、改写历史、合并 PR、关闭 PR 或删除远程分支。
- 提交使用 Conventional Commits，并引用对应 FR/AC。一个提交只包含一个可解释的逻辑变化。
- PR 必须包含变更摘要、FR/AC、测试命令与结果、风险、兼容性或迁移影响、回滚方式；界面变化附截图或录屏。
- PR 的最终审查、合并决定和发布安排由 `root` 与项目组长负责，其他智能体无权自行批准或合并。

## 6. 禁止越权操作

其他智能体不得执行以下操作：

- 擅自新增、删除或改变需求、验收标准、项目范围和优先级；
- 修改不属于自己任务的文件，或修复未获授权的问题；
- 删除、覆盖、批量移动数据或文件，重置工作区，清理他人改动；
- 运行 `git reset --hard`、强制检出覆盖、强制推送或其他可能丢失历史的命令；
- 创建远程仓库、修改 GitHub 数据、合并 PR、发布、部署或操作生产环境；
- 读取、输出、记录或提交密码、密钥、Token、Cookie、个人隐私和真实业务数据；
- 绕过后端权限校验、输入校验、安全限制、测试要求或 `root` 的审查；
- 代表项目组长或 `root` 作出范围、架构、交付日期和验收结论。

## 7. 开发与验证要求

- 开始前确认任务对应的 FR、AC、输入、输出、依赖、可修改文件和禁止触碰范围；信息不足时先报告 `root`。
- 遵守根级工程约定，保持 TypeScript 严格类型，避免无理由使用 `any`，并维持既有分层和模块边界。
- 新增功能至少覆盖正常、边界和失败场景；修复缺陷必须增加能复现问题的测试。
- 完成后运行与改动直接相关的格式检查、类型检查和测试，记录真实命令与结果。不得用“应该通过”代替验证。
- 测试失败时说明失败项、原因和影响；不得修改无关测试、降低校验标准或删除测试来制造通过结果。

## 8. 日志与交接

- 每个智能体每天只维护自己的 `docs/ai-logs/<agent-id>/YYYY-MM-DD.md`，开始重大任务前记录计划，完成后在当天文件中补充实际改动和验证结果。
- 日期变化后必须新建当天文件；历史日志只读，不得追加、覆盖、合并、删除或重命名。
- 任何智能体不得写入其他智能体的日志文件夹。
- 日志必须引用 FR/AC，并记录计划文件、实际文件、测试结果、风险、未完成事项和下一步；不得写入密钥或隐私数据。
- 向 `root` 交接时必须列出：任务状态、修改文件、关键决定、验证命令及结果、已知风险、未完成事项、分支和 PR 状态。
- 未满足验收标准、测试未通过或仍有高风险问题时，不得声明任务完成。

## 9. 必须暂停并上报的情况

遇到以下任一情况，立即停止相关修改并向 `root` 报告：

- 需要修改严格只读文件；
- 任务与需求基线、接口约定或其他智能体工作冲突；
- 需要扩大范围、增加依赖、修改数据库、认证授权或安全策略；
- 发现未提交改动可能被覆盖，或无法判断改动归属；
- 需要删除数据、执行不可逆操作、访问外部服务或修改远程状态；
- 测试持续失败、需求含糊，或继续工作会产生不可控风险。

上报内容应包括当前证据、影响范围、已尝试的安全检查和建议方案。未收到 `root` 的新指令前，不得继续相关操作。

## 10. 任务认领、标签与锁定

- `docs/tasks/` 下的任务文档由 `root` 建立并维护任务范围、FR/AC、依赖、阶段顺序、允许修改范围和验收条件。
- 任务状态只有“待认领”“已认领”“进行中”“待测试”“已完成”“已暂停”六种；未经过 `root` 确认，不得自行改变任务状态、负责人、优先级、范围或阶段顺序。
- 其他智能体认领任务时必须使用唯一且稳定的名称化标签，格式为 `<智能体名称>@<任务标记>`，例如 `DeepSeek@backend`、`ChatGPT@frontend`、`Claude@qa`；标签必须写入对应任务文档的“负责人标签”和自己的日志、分支及 PR 描述。
- 标签中的智能体名称必须使用实际运行智能体的名称，任务标记用于表示 `root`、`backend`、`frontend` 或 `qa` 等任务角色；禁止使用无法识别身份的裸标签，例如 `@backend` 或 `@qa`。
- 一个任务只能有一个负责人标签。已被其他智能体认领的任务，其他智能体只能阅读、评论或向 `root` 提交建议，不得修改任务文档、代码、测试和配置。
- 任务负责人可以修改自己任务文档中的“进度记录”“验证记录”和“交接记录”，并必须同步记录自己的日志和 PR；不得修改任务范围、验收标准、依赖、文件权限和阶段顺序。其他智能体只能阅读、评论或通过 GitHub Issue 提出建议。
- 任务开始后不得擅自更换任务、拆并任务或介入他人任务。确需调整时，必须暂停工作，向 `root` 提交原因、影响、建议方案和待处理改动，等待 `root` 书面确认。
- 当前阶段必须实行“全员完成 → 全员冻结 → T-03 统一检查 → root 解锁”的门禁。`T-01`、`T-02` 完成当前阶段后，必须停止当前阶段开发并标记为“待测试”；在 T-03 检查期间，任何智能体不得开始下一阶段、扩大当前阶段或修改他人任务。
- T-03 检查未通过时，阶段保持冻结；只有 `root` 指定当前阶段的修复范围后，相关负责人才能修复当前阶段，修复完成后再次冻结并交由 T-03 复测。
- 只有 T-03 明确报告当前阶段通过，且 `root` 明确记录“阶段门禁通过/下一阶段解锁”，三人才能继续下一阶段。

## 11. Issue 建议与变更申请

- 范围外问题、阻塞、接口冲突、测试失败、任务调整建议和需求变更建议，统一创建为本项目 GitHub Issue 并提交给 `root`，不得通过直接改文件代替申请。
- GitHub Issue 至少包含：Issue 编号/链接、提出人标签、关联任务编号、关联 FR/AC、类型、现象或证据、影响范围、建议方案、紧急程度和当前状态。
- 类型使用 `bug`、`blocker`、`dependency`、`contract`、`scope-change` 或 `task-change`；状态使用 `open`、`under-review`、`approved`、`rejected` 或 `resolved`。
- Issue 只表达问题和建议，不自动获得代码、任务或外部系统的修改权限。只有 `root` 明确批准后，负责人才能按批准范围继续工作。
- GitHub Issue 是唯一正式的建议和变更申请记录，不在任务文档或 `docs/issues/` 中复制一份作为替代记录；任务文档只保留 Issue 链接和处理状态。
- 涉及需求范围、公共接口、数据库、依赖、权限、安全策略或任务顺序的 Issue，必须由 `root` 记录决定和受影响文件；未批准前保持原任务不变。
- 当前不自动执行远程 GitHub 写操作；需要创建、更新或关闭 GitHub Issue 时，由 `root` 按项目组长授权和仓库权限执行。
