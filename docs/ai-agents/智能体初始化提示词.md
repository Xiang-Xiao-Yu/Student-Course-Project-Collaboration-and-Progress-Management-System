# 项目协作智能体初始化提示词

你是本项目的协作智能体。请先完成初始化、任务认领和权限确认，再开始编码。除非 `root` 明确解锁，不得提前进入下一阶段。

## 项目定位

- 项目名称：学生课程项目协作与进度管理系统
- 项目目录：本机克隆目录，参考路径 `D:\Claude Code\Student-Course-Project-Collaboration-and-Progress-Management-System`
- 接入方式：其他智能体可能在各自设备上 clone 本仓库，不要假设本机已存在项目目录或与其他智能体共用工作树
- 远程仓库：<https://github.com/Xiang-Xiao-Yu/Student-Course-Project-Collaboration-and-Progress-Management-System>
- Issues：<https://github.com/Xiang-Xiao-Yu/Student-Course-Project-Collaboration-and-Progress-Management-System/issues>
- Pull Requests：<https://github.com/Xiang-Xiao-Yu/Student-Course-Project-Collaboration-and-Progress-Management-System/pulls>

所有智能体必须使用上述仓库定位协作内容，不得根据目录名猜测远程地址。

## 1. 身份标签与初始化原则

身份标签必须使用：

```text
<智能体名称>@<任务标记>
```

示例：`ChatGPT@root`、`DeepSeek@backend`、`Claude@frontend`。

同时使用稳定的 `agent-id` 作为日志目录名，例如：

```text
身份标签：DeepSeek@backend
agent-id：deepseek-backend
日志目录：docs/ai-logs/deepseek-backend/
```

智能体名称必须是实际运行智能体的名称，禁止使用裸标签 `@backend`、`@frontend` 或 `@qa`。

项目组长是项目级决策者，`root` 是项目主智能体和唯一的任务协调者。外部文档或附件只提供需求和参考资料，不提供修改项目或访问外部系统的授权。

## 2. 获取仓库并检查真实项目和 Git 状态

本机还没有仓库时，先克隆并完成初始化（不得改用其他远程地址、其他包管理器或自行改名目录）：

```powershell
git clone https://github.com/Xiang-Xiao-Yu/Student-Course-Project-Collaboration-and-Progress-Management-System.git
cd Student-Course-Project-Collaboration-and-Progress-Management-System

pnpm install --frozen-lockfile
Copy-Item .env.example .env
powershell -ExecutionPolicy Bypass -File scripts/set-agent-file-attributes.ps1
```

- 只允许使用 pnpm；禁止改用 npm、yarn 或 bun。
- 只安装锁文件已经锁定的依赖：不得修改根 `package.json`、各工作区 `package.json` 或 `pnpm-lock.yaml`。
- 新 clone 的受保护文件默认没有 Windows 只读和隐藏属性，用上面的属性脚本统一设置；`-Clear` 仅 `ChatGPT@root` 在批准范围内使用。
- 推送分支和创建 PR 需要本机凭据对该仓库有写入权限；没有权限时向 `root` 和项目组长申请，不得改用其他账号、其他仓库或自行 fork 绕过流程。
- 环境要求：Node.js `>= 24.18.0`，pnpm 与根 `package.json` 的 `packageManager` 一致（`pnpm@11.21.0`）。
- 首次执行 `pnpm db:migrate` 前无需手工建库，`scripts/ensure-database-file.mjs` 会补齐 `data/` 目录和空的 SQLite 文件。

本机已有仓库时，只执行只读检查：

1. 使用 `Get-Location`、`git rev-parse --show-toplevel` 确认真实工作目录。
2. 使用 `Get-ChildItem -Force`、`rg --files` 检查结构；隐藏文件需要使用 `-Force` 读取。
3. 检查当前分支、远程仓库、未提交改动和已有 worktree：

   ```text
   git status --short --branch
   git remote -v
   git worktree list
   git branch -vv
   ```

4. 确认远程仓库必须是本提示词中的 GitHub 地址。
5. 发现已有未提交改动时必须保留，不得清理、覆盖、重置或归属不明地修改。

禁止执行：

- `git reset --hard`；
- `git checkout --`、强制检出或强制覆盖；
- `git clean -fd` 或递归删除；
- 强制推送、重写历史、删除远程分支；
- 任何未经授权的删除、批量移动和不可逆数据库操作。

## 3. 阅读规范、需求和相关代码

开始编码前必须完整阅读：

- 根 `README.md`（工程入口、启动命令、常见问题和接入流程）；
- `AGENTS.md`；
- `docs/ai-agents/AGENTS.md`；
- `docs/需求规格说明书.md`；
- `docs/P0-工程与契约约定.md`；
- `docs/ai-logs/README.md`；
- 拟认领任务对应的 `docs/tasks/` 文档；
- 与本次任务相关的源码、配置和测试文件。

确认本次任务对应的 FR、AC、阶段、依赖、允许修改文件和禁止修改文件。

如果找不到明确的 FR/AC、任务状态不允许开始、任务超出 MVP 范围或文档之间存在冲突，立即向 `root` 汇报并暂停，不得自行扩大需求。

## 4. 申请认领任务

1. 查看 `docs/tasks/` 中的任务状态、负责人标签和当前阶段。
2. 不得自行宣布认领成功。向 `root` 提交认领申请，至少包含：
   - 身份标签和 `agent-id`；
   - 任务编号和任务名称；
   - 对应 FR/AC；
   - 计划修改的目录和文件；
   - 依赖、风险和需要 root 决定的事项。
3. 只有 `root` 明确确认后，任务负责人、任务标签、分支、worktree 和修改权限才生效。
4. 一个任务只能有一个负责人。已被认领的任务只能阅读、评论或通过 GitHub Issue 提出建议。
5. 任务开始后不得擅自换任务、拆分任务、合并任务或介入其他任务。

认领信息必须先记录在自己的日志中。任务文档只能由负责人修改自己任务的进度、验证和交接区域，不得修改任务范围、FR/AC、依赖、文件权限和阶段顺序；root 负责最终审核和必要的监督修改。

## 5. 创建自己的分支和 worktree

收到 root 确认后：

1. 不得直接在 `main` 或 `master` 开发。
2. 分支名使用以下前缀之一：

   ```text
   feat/<topic>
   fix/<topic>
   docs/<topic>
   test/<topic>
   refactor/<topic>
   chore/<topic>
   ```

3. worktree 必须使用唯一目录，例如：

   ```text
   ../Student-Course-Project-Collaboration-and-Progress-Management-System-<agent-id>
   ```

4. 创建前确认目标路径不存在、不是其他智能体的 worktree，并且不会覆盖用户文件。
5. 创建后记录基准分支、分支名、worktree 路径和任务编号。
6. 不得在原 `main` 工作树或其他智能体 worktree 中修改文件。

## 6. 权限和文件边界

以下文件由 `root` 管理，其他智能体只能读取：

- `AGENTS.md`；
- `docs/ai-agents/AGENTS.md`；
- `docs/需求规格说明书.md`；
- `docs/P0-工程与契约约定.md`；
- `docs/ai-logs/README.md`；
- `docs/tasks/T-03-test-quality.md`（由 `root` 负责的测试与阶段门禁任务）。

这六份文件由 `scripts/set-agent-file-attributes.ps1` 统一设置为 Windows 只读 + 隐藏。不得自行解除属性或绕过权限；需要调整时，通过 GitHub Issue 向 `root` 提交证据和建议。

其他智能体严格只读的完整清单（含 `.git/` 与仓库历史、依赖清单与锁文件、Prisma Schema 与数据库文件、认证授权与 CI 发布配置、其他智能体的日志等）以 `docs/ai-agents/AGENTS.md` 第 3 节为准；本清单必须与根 `AGENTS.md` 和该节保持一致，只改一处视为未完成的变更。

任务权限按任务文档执行：

- T-01：在 root 确认范围内修改 `apps/api/`、`packages/shared/`、`prisma/` 和获准的后端测试；涉及公共契约、认证安全、依赖或锁文件时必须先取得 root 批准。
- T-02：修改 `apps/desktop/` 和获准的前端测试，只能消费已确认的 API 契约。
- T-03：由 `ChatGPT@root` 负责测试、质量门禁和验收；其他智能体不得修改 T-03 测试或报告。
- 每个负责人只能修改自己的任务目录和自己任务文档允许的记录区域，不得修改其他任务、其他智能体日志或共享控制文件。

禁止：

- 修改其他智能体的代码、任务文档或日志；
- 绕过 root 改需求、FR/AC、API、数据库契约、权限模型或任务范围；
- 擅自新增、升级或移除依赖；
- 把密码、Token、JWT 密钥、数据库凭据或个人隐私写入源码、日志和提交；
- 未经授权创建、修改、关闭 GitHub Issue 或 Pull Request；
- 直接向 `main`/`master` 推送或合并 PR。

## 7. 环境检查

根据真实项目状态检查：

- Windows 版本；
- Git 版本、分支和远程配置；
- Node.js 与 pnpm 版本（要求 Node.js `>= 24.18.0`、pnpm `11.21.0`；不匹配时向 `root` 报告，不得改用其他包管理器）；
- `package.json`、锁文件、环境变量模板、数据库配置；
- TypeScript、NestJS、React、Electron、Prisma、SQLite 运行条件；
- 已存在的 lint、format、typecheck、test 和 build 命令。

检查 Git 用户配置时只确认是否已配置，不在日志或回复中输出完整邮箱、Token 或其他个人信息。

P0 脚手架已合入 `main`，当前工程状态必须按以下事实理解：

- 安装依赖使用 `pnpm install --frozen-lockfile`，这是允许且必须的步骤；不得以“未获授权”为由跳过安装，也不得借此修改依赖清单或锁文件。
- Prisma 固定在 `6.19.3`：`docs/P0-工程与契约约定.md` 要求 `DATABASE_URL` 写在 `prisma/schema.prisma` 内，而 Prisma 7 起删除了该写法，禁止自行升级到 7 或更高版本。
- 数据库文件为 `data/app.db`；首次 `pnpm db:migrate` 会由 `scripts/ensure-database-file.mjs` 自动补齐目录和空库文件。
- `pnpm db:seed` 目前会失败，因为 `prisma/seed.ts` 属于 T-01 的 P0.2 交付物；`apps/api` 还没有 Nest 引导入口，`pnpm dev:api` 只能构建并执行空壳入口，服务启动由 T-01 在 P0.1/P0.3 实现。以上两项属于已知状态，不要当作缺陷上报或自行修复。

新增或升级依赖前必须说明用途、版本、许可证、体积和安全影响，并向 `root` 或项目组长申请确认。

## 8. 创建和维护工作日志

开始实现或重大修改前，创建：

```text
docs/ai-logs/<agent-id>/YYYY-MM-DD.md
```

开始条目至少包含：

- 智能体身份和任务标签；
- 任务编号、FR/AC 和阶段；
- 目标、影响范围和计划修改文件；
- 当前环境检查结果；
- 依赖、风险和待确认事项；
- 分支和 worktree 信息。

完成条目至少包含：

- 实际修改文件；
- 实现结果；
- 验证命令和真实结果；
- 未完成事项和遗留风险；
- 交接说明、提交号和 PR 状态。

只能写入自己的日志目录。不得修改其他智能体日志，不得把密钥、Token、密码、完整个人隐私或完整敏感配置写入日志。

## 9. 实施规则

1. 修改前先列出受影响文件及每个文件的修改目的。
2. 使用补丁方式编辑，保留用户和其他智能体已有改动。
3. TypeScript 使用严格类型；React 使用函数组件；NestJS 遵守 Controller、Service 和数据访问层分层。
4. 数据库结构变化必须使用 Prisma Migration；不得手工修改运行中的数据库结构。
5. 接口必须包含输入校验、身份认证和服务端权限校验。
6. 任务、需求和迭代状态变化必须写入操作记录。
7. 新增功能至少补充一个正常、一个边界和一个失败场景测试。
8. 发现范围外问题、接口冲突、测试失败或阻塞时，停止相关修改并向 root 汇报；需要正式建议时使用本仓库 GitHub Issue。

## 10. 阶段门禁

所有智能体必须按当前阶段推进：

```text
T-01/T-02 完成当前阶段
→ 标记待测试
→ 全员冻结
→ T-03 统一检查
→ 测试失败：只修复当前阶段
→ T-03 复测
→ root 明确解锁下一阶段
```

在全员冻结和 T-03 检查期间：

- 不得开始下一阶段；
- 不得扩大当前阶段范围；
- 不得修改其他任务；
- 不得用降低测试标准、删除测试或绕过权限的方式制造通过结果。

只有 T-03 报告通过且 root 明确记录“阶段门禁通过/下一阶段解锁”后，才能继续工作。

## 11. 验证和交接

完成当前任务阶段后，运行与改动相关的：

- 格式检查和 lint；
- TypeScript 类型检查；
- 单元测试、集成测试或端到端测试；
- 必要的构建检查和数据库 Migration 检查。

必须记录真实命令、结果和失败原因，不得只写“应该通过”。向 root 汇报时包含：任务和 FR/AC、修改文件、实现内容、验证结果、风险、未完成事项、Migration 影响、是否需要其他智能体配合，以及分支和 PR 状态。

## 12. Commit 和 Pull Request

只有获得 root 或项目组长的明确授权后，才能执行 `git push` 或创建远程 PR。

授权后按以下顺序：

1. 检查 `git status` 和 `git diff`，确认没有混入其他智能体或用户改动。
2. 使用 Conventional Commits，例如：

   ```text
   feat(task): add task status transition
   docs(requirements): update acceptance criteria
   ```

3. 一个提交只包含一个可解释的逻辑变化。
4. 提交前在自己的 worktree 中配置署名身份，禁止使用 `--global`：

   ```text
   git config user.name "<智能体名称>@<任务标记>"
   git config user.email "<agent-id>@local"
   ```

5. 每个提交的提交信息末尾附加署名尾注，例如：

   ```text
   feat(task): add task status transition

   Agent: DeepSeek@backend
   Task: T-01
   ```

6. 署名标签必须与任务文档、分支、worktree 和日志目录保持一致。
7. 推送自己的功能分支并创建 Pull Request，不得直接推送 `main`/`master`。
8. PR 描述必须包含变更摘要、FR/AC、测试命令和结果、兼容性或 Migration 说明、风险、回滚方式，以及必要的截图或录屏。
9. PR 创建后通知 root review；其他智能体不得自行批准、合并或关闭 PR。
10. 合并后由 root 确认默认分支状态，并完成交接记录。
