## 2. 项目概述

### 2.1 项目背景

学生课程项目通常使用聊天记录、表格和零散文档管理任务，容易出现以下问题：

- 任务负责人不明确；
- 需求和任务没有关联；
- 截止日期和逾期情况不直观；
- 会议决定没有转化为可跟踪任务；
- 阶段成果和验收记录难以集中保存；
- 项目进度只能依靠人工汇总。

本系统为学生团队提供一个统一的项目协作空间，将“需求—任务—迭代—会议—验收—统计”串联起来。

### 2.2 项目目标

1. 让团队成员能清楚知道当前项目要做什么、谁负责、什么时候完成。
2. 让项目负责人能查看需求完成率、任务状态和迭代进度。
3. 让会议结论、阶段验收和整改任务能够被记录和追踪。
4. 为课程项目提供可复查的过程资料，包括操作记录、进度数据和验收结果。

### 2.3 产品边界

首版是面向小型学生团队的项目协作工具，不是通用企业项目管理平台。首版不处理财务、考勤、即时聊天、在线文档实时协作和复杂组织架构。

## 3. 用户与角色

### 3.1 用户角色

| 角色 | 说明 |
|---|---|
| 平台管理员 | 管理用户和平台基础数据，可查看所有项目；首版可以只保留一个预置账号 |
| 项目负责人 | 创建项目、管理成员、维护需求和迭代、分配任务、进行阶段验收 |
| 项目成员 | 查看项目资料，创建或处理任务，更新任务状态，发布评论和会议行动项 |
| 观察者 | 查看项目进度和验收资料，不能修改业务数据，适用于教师或旁听成员 |

### 3.2 使用者画像

- **项目负责人**：需要安排任务、检查风险、准备课程汇报材料。
- **项目成员**：需要查看自己的待办、更新任务进展、提交成果说明。
- **教师或观察者**：需要快速查看项目是否按计划进行以及阶段成果是否通过。

## 4. 业务流程

### 4.1 项目主流程

```text
注册或登录
  → 创建项目
  → 邀请成员并分配角色
  → 建立需求和验收标准
  → 将需求拆分为任务
  → 创建迭代并安排截止日期
  → 成员执行任务并更新状态
  → 负责人审核任务和阶段成果
  → 记录阶段验收
  → 查看统计并归档项目
```

### 4.2 会议辅助流程

```text
创建会议
  → 填写议程和参会人员
  → 记录纪要与决定
  → 生成行动项
  → 将行动项转为任务
  → 跟踪行动项完成情况
```

### 4.3 GitHub 辅助流程

```text
配置仓库地址
  → 创建或选择系统任务
  → 手动关联 GitHub Issue
  → 在任务中查看 Issue 链接和基本状态
```

首版只做手动关联或单向读取，不做系统任务与 GitHub Issue 的双向自动同步。

## 6. 详细功能需求

### 6.1 FR-01 用户注册、登录和个人资料

系统应支持：

- 用户注册；
- 用户名和密码登录；
- 退出登录；
- 修改密码；
- 修改昵称和头像；
- 查看个人负责的任务；
- 禁用用户；
- 登录失败和会话过期提示。

业务规则：

1. 用户名不能重复。
2. 密码长度至少为 8 位，不能明文保存。
3. 禁用用户不能登录，也不能继续访问项目数据。
4. 退出登录后，服务端必须使旧的访问令牌失效，旧令牌不能继续调用受保护接口。

### 6.2 FR-02 项目管理

项目负责人可以：

- 创建项目；
- 编辑项目名称、简介、开始日期和结束日期；
- 设置项目状态；
- 查看项目概览；
- 归档项目；
- 删除项目。

项目状态：

```text
规划中 → 进行中 → 已完成 → 已归档
             ↘ 已暂停
已暂停 → 进行中
```

业务规则：

1. 项目结束日期不能早于开始日期。
2. 已归档项目只读，不能新增或修改任务。
3. 删除项目必须二次确认。
4. 删除项目属于高风险操作，必须记录操作日志。
5. 项目处于“已暂停”时不能新增业务数据；恢复后回到“进行中”。

### 6.3 FR-03 成员与权限管理

项目负责人可以：

- 邀请已有用户加入项目；
- 为成员设置项目角色；
- 修改成员角色；
- 移除成员；
- 查看成员负责的任务和完成情况。

业务规则：

1. 只有项目成员可以访问项目内部数据。
2. 任务负责人必须是当前项目成员。
3. 项目负责人不能移除自己，必须先移交项目负责人权限。
4. 成员被移除后，历史评论和操作记录仍然保留。

### 6.4 FR-04 需求管理

系统应支持：

- 创建需求；
- 编辑需求；
- 删除需求；
- 设置需求优先级；
- 填写需求描述；
- 填写验收标准；
- 关联多个任务；
- 查看需求对应的任务完成情况。

需求字段：

| 字段 | 要求 |
|---|---|
| 需求编号 | 项目内唯一，例如 REQ-001 |
| 标题 | 必填，长度 1–100 个字符 |
| 描述 | 说明用户需要什么功能以及使用场景 |
| 提出人 | 自动记录当前用户 |
| 优先级 | 高、中、低 |
| 验收标准 | 至少一条可检查的标准 |
| 状态 | 草稿、已确认、开发中、待验收、已完成、已拒绝 |
| 关联任务 | 一个需求可关联多个任务 |

需求状态：

```text
草稿 → 已确认 → 开发中 → 待验收 → 已完成
                                  ↘ 已拒绝
```

### 6.5 FR-05 任务管理与看板

系统应支持：

- 创建、编辑和删除任务；
- 设置标题、描述、负责人、优先级和截止日期；
- 设置任务标签；
- 关联需求和迭代；
- 填写预估工时；
- 通过看板拖拽任务；
- 添加评论、附件和完成说明；
- 查看任务状态变化记录。

任务状态：

```text
待规划 → 待开始 → 进行中 → 待审核 → 已完成
                      ↓
                    已阻塞
```

业务规则：

1. 任务标题、创建人和项目归属是必填信息。
2. 任务负责人必须属于当前项目。
3. 任务截止日期不能早于项目开始日期。
4. 任务进入“待审核”前，应填写完成说明或提交关联成果；项目负责人审核通过后才能进入“已完成”。
5. 任务状态每次变化都必须记录操作人、原状态、新状态和时间。
6. 已完成任务可以重新打开，重新打开必须填写原因。

### 6.6 FR-06 迭代计划管理

项目负责人可以：

- 创建迭代；
- 设置迭代名称、目标、开始日期和结束日期；
- 将任务加入或移出迭代；
- 查看迭代完成率；
- 关闭迭代；
- 将未完成任务移入下一迭代。

迭代状态：

```text
未开始 → 进行中 → 已完成
              ↘ 已取消
```

迭代统计至少包括任务总数、已完成数、进行中数、阻塞数、逾期数和完成率。

### 6.7 FR-07 评论与操作记录

任务、需求和会议记录支持评论。系统应支持：

- 发布评论；
- 修改自己的评论；
- 删除自己的评论；
- 查看评论时间和作者；
- 查看对象的操作记录。

操作记录至少包含：

- 操作人；
- 操作类型；
- 操作对象；
- 修改前内容；
- 修改后内容；
- 操作时间。

### 6.8 FR-08 会议纪要与行动项

系统应支持：

- 创建会议；
- 设置会议主题、时间和参会人员；
- 填写议程；
- 编辑会议纪要；
- 记录会议决定；
- 创建行动项；
- 为行动项设置负责人和截止日期；
- 将行动项转换为普通任务；
- 查询历史会议。

会议行动项至少包含标题、负责人、截止日期、状态和关联会议。

会议行动项状态限定为：待处理、进行中、已完成、已取消。

### 6.9 FR-09 阶段验收

项目负责人可以创建阶段验收记录，记录：

- 验收阶段名称；
- 验收目标；
- 验收时间；
- 参与人员；
- 验收标准；
- 验收结果；
- 未通过原因；
- 整改任务；
- 相关附件。

验收结果：

```text
未开始、验收中、已通过、未通过
```

验收未通过时，系统应允许创建整改任务，并关联到对应需求或迭代。

### 6.10 FR-10 项目统计与仪表盘

项目首页至少显示：

- 项目整体完成率；
- 任务总数；
- 各状态任务数量；
- 逾期任务数量；
- 各成员任务数量；
- 各迭代完成率；
- 需求完成率；
- 最近操作记录；
- 即将到期任务。

首版图表包括：

- 任务状态分布图；
- 成员任务分布图；
- 迭代完成率图；
- 任务完成趋势图；
- 简单燃尽图。

甘特图属于扩展功能，不能影响核心流程交付。

### 6.11 FR-11 搜索、筛选和导出

系统应支持：

- 按标题搜索需求和任务；
- 按负责人筛选；
- 按状态筛选；
- 按优先级筛选；
- 按标签筛选；
- 按迭代筛选；
- 按截止日期筛选；
- 导出任务列表为 CSV；
- 导出基础项目进度报告。

筛选条件可以组合使用，清空筛选后恢复全部结果。

### 6.12 FR-12 附件管理

附件功能属于首版建议功能。系统应支持：

- 上传附件；
- 下载附件；
- 查看文件名、大小、上传人和上传时间；
- 删除自己上传的附件；
- 在需求、任务、会议和验收记录中关联附件。

安全要求：

- 单个文件默认不超过 10MB；
- 限制允许的扩展名；
- 文件保存路径不能由用户直接控制；
- 禁止通过文件名访问任意服务器路径。

### 6.13 FR-13 GitHub Issue 关联

系统应支持：

- 保存 GitHub 仓库地址；
- 通过 Issue 编号或 URL 关联任务；
- 显示 Issue 标题、编号、链接和读取到的状态；
- 手动刷新 Issue 基本信息；
- 在任务详情页打开 GitHub Issue。

首版不实现 GitHub Issue 和系统任务的双向自动同步，也不自动创建、关闭或修改 GitHub Issue。

GitHub API 不可用时，任务管理、需求管理和统计功能仍应正常使用。

### 6.14 FR-14 数据备份与恢复

系统应支持：

- 导出项目数据；
- 手动备份 SQLite 数据库；
- 查看最近一次备份时间；
- 从备份文件恢复数据。

自动云备份不属于首版范围。

## 8. 数据需求

### 8.1 核心实体

| 实体 | 主要字段 |
|---|---|
| User | id、用户名、密码哈希、昵称、头像、状态、创建时间 |
| Project | id、名称、简介、开始日期、结束日期、状态、负责人 |
| ProjectMember | 项目 id、用户 id、项目角色、加入时间 |
| Requirement | 编号、标题、描述、优先级、验收标准、状态、提出人 |
| Task | 标题、描述、负责人、优先级、状态、截止日期、预估工时、完成说明、完成时间 |
| Tag | 名称、颜色、所属项目 |
| Iteration | 名称、目标、开始日期、结束日期、状态 |
| Comment | 所属对象、评论内容、作者、创建时间、修改时间 |
| ActivityLog | 操作人、对象、操作类型、修改前值、修改后值、时间 |
| Meeting | 主题、时间、议程、纪要、决定、创建人 |
| MeetingAction | 行动项标题、负责人、截止日期、状态、关联会议 |
| Acceptance | 阶段、目标、标准、结果、原因、验收人、时间 |
| Attachment | 原文件名、存储名、大小、类型、上传人、关联对象 |
| GithubIssueLink | 仓库地址、Issue 编号、任务 id、同步时间 |

### 8.2 主要关系

```text
User        N —— N Project
Project     1 —— N Requirement
Project     1 —— N Task
Requirement 1 —— N Task
Iteration   1 —— N Task
Task        1 —— N Comment
Task        1 —— N ActivityLog
Project     1 —— N Meeting
Project     1 —— N Acceptance
```

### 8.3 数据一致性要求

1. 任务、需求、迭代和评论必须归属于同一个项目。
2. 删除项目时必须处理或禁止删除关联任务、评论和日志。
3. 项目成员被移除后，历史业务记录不能丢失。
4. 状态、角色和优先级使用受限枚举值，不能保存任意字符串。
5. 数据库结构变化必须通过 Prisma Migration 管理。

## 9. 非功能需求

### 9.1 性能

- 普通页面首次加载时间不超过 3 秒；
- 常规任务列表查询响应时间不超过 1 秒；
- 首版支持至少 20 名用户同时访问；
- 单个项目支持至少 10,000 条任务记录；
- 图表加载过程中显示加载状态。

### 9.2 安全

- 密码使用安全哈希算法保存；
- 所有受保护接口都必须验证身份；
- 所有修改操作都必须进行服务端权限检查；
- 防止 SQL 注入、路径穿越和越权访问；
- JWT 密钥、GitHub Token 和数据库凭据只能通过环境变量提供；
- 密钥不能提交到 Git，也不能写入日志；
- GitHub Token 在界面中不得以明文显示。

### 9.3 可用性

- 空数据页面显示明确的引导文字；
- 请求失败时显示可理解的错误信息；
- 删除操作必须二次确认；
- 离开未保存表单时给出提示；
- 日期、状态和优先级使用统一的显示方式；
- 主要操作支持键盘访问。

### 9.4 可维护性

- 前端使用 TypeScript 严格类型检查；
- React 页面使用函数组件；
- NestJS 按 Controller、Service、数据访问层分层；
- API 提供统一响应格式和错误码；
- 关键 Service 逻辑有单元测试；
- 需求、接口、数据库和前端行为保持一致。

### 9.5 兼容性

- 首版客户端支持 Windows 11；
- 开发环境应支持现代 Chromium 浏览器；
- 后端应能在 Windows 本机或局域网主机运行；
- SQLite 用于开发和课程演示，数据库访问必须通过 Prisma。

## 10. MVP 与后续范围

### 10.1 MVP 必须完成

1. 登录和身份认证；
2. 项目、成员和基础角色权限；

## 11. 验收标准

### AC-01 登录与访问

用户注册后可以登录和退出。未登录用户访问项目页面时必须被拦截。

### AC-02 项目与成员

负责人创建项目并邀请两名成员。成员登录后可以看到加入的项目，不能看到未加入项目的数据。

### AC-03 需求拆分

负责人创建需求并填写验收标准，随后创建多个任务。需求详情页可以看到关联任务及其完成情况。

### AC-04 任务流转

成员将任务从“待开始”改为“进行中”，完成后填写完成说明并提交审核，负责人审核后改为“已完成”。系统可以查看完整状态变更记录；审核不通过时任务保持“待审核”并显示原因。

### AC-05 迭代统计

负责人创建一个迭代并加入任务。系统正确显示任务总数、已完成数、阻塞数、逾期数和完成率。

### AC-06 会议行动项

用户创建会议并填写纪要，从会议中生成一个行动项。行动项可以设置负责人、截止日期和状态，并可转换为普通任务。

### AC-07 阶段验收

负责人创建阶段验收并选择“未通过”，系统允许填写原因并生成整改任务。整改完成后可以再次记录验收结果。

### AC-08 权限控制

普通成员不能删除项目、移除成员或修改项目权限。观察者可以查看数据，但不能创建或修改业务对象。

### AC-09 查询与导出

用户可以组合负责人、状态、优先级和截止日期筛选任务，并成功导出 CSV 文件。

### AC-10 异常处理

空项目、无效日期、重复用户名、无权限访问、网络请求失败和不存在的数据都应显示明确提示，不能导致程序崩溃。

## 13. 项目约束与假设

1. 团队规模为三人，所有成员都应承担开发或测试工作。
2. 项目首版服务于小型学生团队，目标用户量不超过 50 人。
3. 首版不依赖付费云服务，GitHub API 不可用时核心功能仍需可运行。
4. Electron 负责桌面客户端展示，NestJS 提供业务 API，SQLite 保存课程演示数据。
5. 具体技术版本以项目初始化时锁定的 `package.json` 和工具配置为准。
6. 任何超出本文档范围的功能，都必须先更新需求、评估工期，再加入迭代计划。
