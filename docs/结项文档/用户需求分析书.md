## 1. 引言

### 1.1 编写目的

本文档从课程项目参与者的角度，分析系统应解决的问题，明确不同用户的使用目标、业务流程、功能需求和使用约束，为项目结项时的需求追溯、成果说明和验收提供依据。

需求分析重点回答“谁使用系统、需要完成什么工作、系统应达到什么要求”。各项需求是否已经实现、测试是否通过，由测试报告和最终验收报告分别说明。

### 1.2 分析依据

本文档依据项目已确认的[《软件需求规格说明书》0.1.4](../需求规格说明书.md)，结合其中的用户画像、业务流程、权限矩阵和验收标准进行整理。文中的功能编号 FR、验收标准编号 AC 及优先级沿用该需求基线。

本文档作为需求基线的用户视角说明，不单独调整功能范围或验收口径。后续若产生新增或变更需求，应按项目既有变更流程更新正式需求基线，再同步相关文档。

### 1.3 术语说明

| 术语     | 含义                                                           |

## 2. 项目背景与问题分析

### 2.1 项目背景

学生课程项目通常由少量成员在有限周期内共同完成。团队除了编写代码，还需要明确需求、安排分工、跟踪进度、记录会议以及整理阶段成果。若这些信息分散在聊天记录、电子表格和多个文档中，成员就需要反复核对不同资料，负责人也难以直接判断当前进展。

本系统面向小型学生课程项目团队，提供统一的项目协作空间，将需求、任务、迭代、会议、验收和统计关联起来，使团队能够围绕同一组项目数据开展工作。

### 2.2 主要问题与用户诉求

| 现有问题                   | 对项目工作的影响                                       | 用户诉求                                             |
| -------------------------- | ------------------------------------------------------ | ---------------------------------------------------- |
| 分工记录分散，负责人不清楚 | 成员难以确定自己应完成的事项，也可能出现遗漏或重复工作 | 每项任务有明确负责人、优先级和截止日期               |
| 需求与任务缺少关联         | 完成了哪些需求、哪些需求尚未落实难以核对               | 能从需求查看关联任务及完成情况                       |
| 进度依赖口头汇报和人工统计 | 负责人难以及时发现逾期、阻塞和阶段风险                 | 通过看板、迭代及统计页面了解实际进展                 |
| 会议决定停留在纪要中       | 会后事项缺少负责人和后续跟踪                           | 将会议行动项转为可执行、可跟踪的任务                 |
| 完成任务与通过验收混在一起 | 成果缺少审核依据，未通过事项难以闭合                   | 保留任务审核、阶段验收和整改记录                     |
| 过程资料分散               | 课程汇报和结项时需要重新收集、核对材料                 | 集中保存操作记录、进度数据和验收资料，并支持基础导出 |

### 2.3 建设目标

1. 使项目成员能够清楚了解工作内容、责任归属、完成时限和当前状态。
2. 使项目负责人能够按需求和迭代组织任务，及时识别逾期及阻塞事项。
3. 使会议决定、任务执行、成果审核和整改过程能够连续追踪。
4. 使教师或观察者能够查看项目进度和阶段成果，减少资料反复传递。
5. 为课程汇报和结项提供可核对的项目过程资料。

## 3. 用户与使用环境分析

### 3.1 用户角色及核心需求

| 用户角色   | 主要职责                                               | 核心需求                                                     |
| ---------- | ------------------------------------------------------ | ------------------------------------------------------------ |
| 平台管理员 | 管理用户和平台基础数据，可查看所有项目                 | 管理账号状态，处理平台管理事项；首版可使用一个预置管理员账号 |
| 项目负责人 | 创建项目、管理成员、维护需求和迭代、分配任务、组织验收 | 统一安排工作，掌握进度和风险，审核成果，整理项目报告         |
| 项目成员   | 参与项目执行，创建或处理任务，更新状态，参与评论及会议 | 查看本人待办及关联需求，更新进展，说明成果，记录问题和行动项 |
| 观察者     | 查看项目资料，了解进度和验收情况                       | 在只读权限下快速查看项目过程与成果，适用于教师或旁听成员     |

教师可以作为观察者参与项目，无需为此增加独立的教师业务模块。项目角色决定业务操作权限，角色限制应同时在界面和服务端生效。

### 3.2 典型使用场景

**项目启动场景。** 负责人创建课程项目，填写基本信息及计划日期，邀请已有用户加入项目并分配角色。成员登录后查看已加入的项目，了解团队分工。

**日常执行场景。** 成员查看本人负责的任务，通过关联需求了解目标和验收标准；开始工作后更新任务状态，遇到问题时记录阻塞或发表评论，完成后填写说明并提交审核。

**阶段计划场景。** 负责人创建迭代、安排任务，并查看任务总量、完成率、阻塞和逾期情况，据此调整后续工作安排。

**会议跟进场景。** 团队记录会议议程、纪要及决定，将需要继续执行的事项登记为行动项，指定负责人和截止日期，并按需要转换为任务。

**成果检查场景。** 负责人依据阶段验收标准检查成果，记录通过或未通过结果。未通过事项形成整改任务，整改完成后再次记录验收结果。

**汇报与结项场景。** 负责人查看项目统计、筛选任务并导出基础资料；教师或观察者查看项目进度、历史记录和验收结果。

### 3.3 使用环境与规模

- 首版客户端面向 Windows 11，使用 Electron 提供桌面入口。
- 后端运行在 Windows 本机或局域网主机，开发环境支持现代 Chromium 浏览器。
- 系统面向小型学生团队，目标用户量不超过 50 人；本项目开发团队规模为三人。
- 首版采用 SQLite 保存开发与课程演示数据，不依赖付费云服务。
- GitHub 等外部服务不可用时，核心项目管理流程仍应可运行。

## 4. 业务流程分析

### 4.1 核心业务流程

```text
用户注册、登录
    ↓
负责人创建项目，邀请成员并设置角色
    ↓
建立需求，填写验收标准
    ↓
将需求拆分为任务，明确负责人、优先级和截止日期
    ↓
创建迭代，将任务纳入阶段计划
    ↓
成员执行任务，更新状态并记录问题
    ↓
成员填写完成说明，提交负责人审核
    ↓
负责人审核任务，组织阶段验收
    ↓
查看统计、导出资料，按项目状态流程完成归档
```

任务审核不通过时，任务保持“待审核”并显示原因。阶段验收未通过时，记录未通过原因并创建整改任务；整改完成后可以再次记录验收结果。任务审核与阶段验收是两个不同层次的检查环节。

### 4.2 会议行动项流程

```text
创建会议 → 设置主题、时间、参会人员和议程
    → 记录纪要与决定 → 建立行动项
    → 指定负责人和截止日期 → 按需要转换为任务
    → 跟踪执行状态
```

会议记录保存讨论背景，行动项明确后续工作，普通任务承接具体执行。通过关联关系，团队可以从执行事项回查其会议来源。

### 4.3 关键业务规则

| 业务对象 | 应遵循的规则                                                                                                     |
| -------- | ---------------------------------------------------------------------------------------------------------------- |
| 项目     | 结束日期不能早于开始日期；暂停期间不能新增业务数据，恢复后回到进行中；归档后只读；删除须二次确认并记录日志       |
| 成员     | 非管理员用户仅能访问已加入项目的内部数据；负责人移除自己前须先移交负责人权限；移除成员后保留其历史评论和操作记录 |
| 需求     | 项目内需求编号唯一，标题为 1～100 个字符，至少包含一条可检查的验收标准                                           |
| 任务     | 标题、创建人、项目归属必填；负责人属于当前项目；截止日期不能早于项目开始日期                                     |
| 任务审核 | 进入待审核前应填写完成说明或提交关联成果；负责人审核通过后才能进入已完成；重新打开已完成任务须填写原因           |
| 状态记录 | 任务状态变化应记录操作人、原状态、新状态和时间；需求、迭代状态变化也应保留操作记录                               |
| 阶段验收 | 保留验收目标、标准、结果、参与人员及时间；未通过时记录原因，并支持关联整改任务                                   |

### 4.4 业务状态

| 对象       | 状态及主要流程                                                                         |
| ---------- | -------------------------------------------------------------------------------------- |
| 项目       | 规划中 → 进行中 → 已完成 → 已归档；进行中可暂停，已暂停可恢复为进行中                  |
| 需求       | 草稿 → 已确认 → 开发中 → 待验收 → 已完成；待验收可转为已拒绝                           |
| 任务       | 待规划 → 待开始 → 进行中 → 待审核 → 已完成；执行中可标记已阻塞；已完成可按规则重新打开 |
| 迭代       | 未开始 → 进行中 → 已完成；进行中可转为已取消                                           |
| 会议行动项 | 待处理、进行中、已完成、已取消                                                         |
| 阶段验收   | 未开始、验收中、已通过、未通过                                                         |

## 5. 功能需求分析

### 5.1 功能范围与优先级

M（Must）为首版必须完成；S（Should）为建议功能，可在时间不足时延后；C（Could）为后续扩展。扩展功能应在 MVP 稳定且按项目流程获准后安排。

| 功能编号 | 功能模块                   | 优先级 | 对应用户诉求                             |
| -------- | -------------------------- | ------ | ---------------------------------------- |
| FR-01    | 用户注册、登录和个人资料   | M      | 安全进入系统，管理个人身份信息和本人待办 |
| FR-02    | 项目创建与项目状态管理     | M      | 集中管理课程项目及其生命周期             |
| FR-03    | 成员邀请与角色权限         | M      | 明确协作成员及操作边界                   |
| FR-04    | 需求管理                   | M      | 说明要完成什么，并跟踪需求落实情况       |
| FR-05    | 任务管理与看板             | M      | 明确分工、时限和执行状态                 |
| FR-06    | 迭代计划管理               | M      | 按阶段安排工作和检查进度                 |
| FR-07    | 评论与操作记录             | M      | 围绕业务事项讨论并保留变更依据           |
| FR-08    | 会议纪要与行动项           | M      | 保存会议决定，跟进会后事项               |
| FR-09    | 阶段验收                   | M      | 记录成果检查及整改过程                   |
| FR-10    | 项目统计与仪表盘           | M      | 查看完成情况、任务分布和风险             |
| FR-11    | 搜索、筛选和 CSV 导出      | M      | 快速定位事项并整理汇报资料               |
| FR-12    | 附件管理                   | S      | 将相关文件与业务记录集中关联             |
| FR-13    | GitHub Issue 关联          | S      | 在系统任务中查阅关联的代码协作事项       |
| FR-14    | 数据备份与恢复             | S      | 通过手动备份和恢复保存项目数据           |
| FR-15    | 甘特图、桌面通知和高级报表 | C      | 提供更丰富的计划展示和辅助信息           |

### 5.2 用户注册、登录和个人资料（FR-01）

用户需要通过用户名和密码注册、登录、退出，修改密码及昵称，查看本人负责的任务。系统应提示重复用户名、登录失败和会话过期等情况。密码至少为 8 位，不能明文保存；被禁用的用户不能登录或继续访问项目数据，退出后旧访问令牌应失效。

用户通过“更换图片”或相机按钮打开系统文件选择器，选择有效图片后自动上传头像，不需要另点上传或保存。头像支持 JPEG/JPG、PNG、WebP，单个文件不超过 10 MiB；系统应校验实际文件内容并存放在服务端受控目录。

头像和昵称独立保存。自动上传不能提交或丢弃未保存的昵称，保存昵称不能重复上传头像。取消选图或读取、上传失败时保留原头像；成功后刷新、重新登录及同一服务上的其他客户端仍能读取新头像。相关操作进行期间应避免冲突提交，界面与错误信息不能泄露用户本地路径或服务端内部路径。

### 5.3 项目与成员管理（FR-02、FR-03）

负责人需要创建项目，维护名称、简介、起止日期及状态，并查看项目概览。系统应支持暂停、恢复、完成和归档等状态管理，对无效日期、归档只读和删除确认给出明确处理。

负责人可以邀请已有用户、设置或调整角色、移除成员，并查看成员负责的任务及完成情况。成员登录后应能看到自己加入的项目，不能访问其他项目内部数据。系统需要检查任务负责人的项目成员身份，人员离开项目后仍保留历史记录。

### 5.4 需求管理（FR-04）

团队需要统一记录需求的标题、描述、提出人、优先级、验收标准和状态，支持创建、编辑及按权限删除。需求描述应说明用户需要的能力和使用场景，验收标准应能够被检查。

一个需求可以关联多个任务。用户从需求详情查看任务及完成情况，判断需求是否已经得到落实，避免只统计任务数量而无法解释需求完成程度。

### 5.5 任务管理与看板（FR-05）

团队需要创建、编辑任务，设置标题、描述、负责人、优先级、截止日期、标签和预估工时，并关联需求及迭代。看板应支持按状态组织任务及拖拽流转，使成员能够直接了解待开始、进行中、待审核、已完成和已阻塞等情况。

成员完成工作后填写完成说明或提交关联成果，再提交审核；负责人审核通过后任务才能完成。系统应保留完整的状态变化记录，已完成任务重新打开时记录原因。任务的删除操作受角色权限约束。

任务支持围绕事项发表评论和查看历史记录。任务中的通用附件能力按 FR-12 的 S 级范围安排，不能因为任务详情提到附件，就将整个附件管理模块纳入 M 级范围；FR-01 的头像上传仍属于必做功能。

### 5.6 迭代计划管理（FR-06）

负责人需要为阶段工作设置迭代名称、目标和起止日期，将任务加入或移出迭代，关闭迭代，并将未完成任务移入下一迭代。

迭代应展示任务总数、已完成数、进行中数、阻塞数、逾期数和完成率，帮助负责人判断阶段目标的完成情况及后续安排。

### 5.7 评论与操作记录（FR-07）

用户需要在任务、需求和会议记录下评论，查看作者及时间，并修改或删除自己的评论。观察者只读，不具备发布评论等业务写入权限。

系统应保存操作人、操作类型、操作对象、修改前后内容和时间。操作记录应帮助团队回查状态及内容变化的原因，为任务审核、阶段检查和课程过程评价提供依据。

### 5.8 会议纪要与行动项（FR-08）

团队需要创建和查询会议，维护主题、时间、参会人员、议程、纪要和决定。会议行动项应包含标题、负责人、截止日期、状态及关联会议。

行动项可以转换为普通任务，后续按照任务流程跟踪执行。这样既能保留会议讨论背景，也能明确会后工作由谁负责、何时完成。

### 5.9 阶段验收（FR-09）

负责人需要创建阶段验收记录，填写阶段名称、目标、时间、参与人员和验收标准，并记录验收结果。验收未通过时，应填写原因，创建整改任务，并支持关联到对应需求或迭代。整改完成后可以再次记录验收结果。

相关附件按 FR-12 的建议范围处理。验收记录应保留检查依据和整改关联，使团队能够说明成果是否达标以及问题如何处理。

### 5.10 项目统计与仪表盘（FR-10）

负责人需要在项目首页查看整体完成率、任务总数、各状态数量、逾期任务、成员任务数量、迭代完成率、需求完成率、最近操作及即将到期任务。

首版图表包括任务状态分布、成员任务分布、迭代完成率、任务完成趋势和简单燃尽图。图表应基于项目数据展示，在加载时提供反馈，并能与对应明细核对。性能指标是验收目标，不能用图表存在或页面可打开替代数据与性能验证。

### 5.11 搜索、筛选和导出（FR-11）

用户需要按标题搜索需求和任务，并根据负责人、状态、优先级、标签、迭代及截止日期组合筛选。清空筛选后恢复全部结果，无匹配结果时应有明确提示。

系统应支持导出任务 CSV 和基础项目进度报告。导出操作应遵守权限矩阵，项目报告由管理员或项目负责人导出。PDF 进度报告属于后续扩展，不作为本项首版必须能力。

### 5.12 建议及后续功能（FR-12～FR-15）

| 功能                            | 用户预期与范围约束                                                                                                         |
| ------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| 附件管理（S）                   | 上传、下载、查看文件信息，删除本人上传文件，并关联需求、任务、会议或验收记录；单文件默认不超过 10 MB，限制扩展名及存储路径 |
| GitHub Issue 关联（S）          | 配置仓库地址，通过编号或 URL 关联任务，查看标题、编号、链接和读取到的状态，并手动刷新；不自动创建、关闭或修改远端 Issue    |
| 数据备份与恢复（S）             | 导出项目数据、手动备份 SQLite、查看最近备份时间并从文件恢复；不包括自动云备份                                              |
| 甘特图、桌面通知和高级报表（C） | 在核心流程稳定后另行安排，不作为首版核心交付的前置条件                                                                     |

| 创建项目并邀请成员 | 已登录且有相应权限的负责人或管理员       | 创建项目，填写计划日期，邀请两名已有用户并设置角色               | 成员能查看已加入项目；无效日期、无权限操作有提示；未加入项目的数据不可见     | FR-02、FR-03；AC-02、AC-08、AC-10 |
| 将需求拆分为任务   | 已加入项目且具备创建权限的用户           | 创建需求并填写验收标准，创建多个关联任务，安排负责人和截止日期   | 需求详情显示关联任务和完成情况；任务负责人须为当前项目成员，无效日期被校验   | FR-04、FR-05；AC-03、AC-10        |

| 验收与整改         | 项目负责人，已有阶段成果及验收标准       | 创建验收，记录未通过原因，生成整改任务，整改后再次验收           | 保留结果和整改关联；普通成员不能执行阶段验收，观察者只读                     | FR-09、FR-05；AC-07、AC-08        |
| 查询与导出任务     | 已加入项目的用户；导出者具备相应权限     | 组合筛选任务，查看结果，清空筛选；有权限者导出 CSV               | 结果对应筛选条件，清空后恢复全部结果；空结果、失败及无权限访问有提示         | FR-11；AC-09、AC-08、AC-10        |

## 7. 数据需求与权限需求

### 7.1 主要业务数据

| 数据类别       | 主要内容                                                               | 用户使用目的                           |
| -------------- | ---------------------------------------------------------------------- | -------------------------------------- |
| 用户与成员关系 | 用户名、昵称、头像、账号状态、项目角色、加入时间                       | 识别协作成员，确定项目访问及操作权限   |
| 项目           | 名称、简介、起止日期、状态、负责人                                     | 建立统一协作空间和项目计划             |
| 需求           | 编号、标题、描述、优先级、标准、状态、提出人                           | 明确工作目标并追溯需求完成情况         |
| 任务与标签     | 标题、描述、负责人、状态、优先级、截止日期、标签、工时、完成说明及时间 | 支持分工、执行、审核及查询统计         |
| 迭代           | 名称、目标、日期、状态及所属任务                                       | 按阶段组织工作并查看完成情况           |
| 评论与操作记录 | 内容、作者、时间、操作对象及修改前后信息                               | 保留讨论内容和变更过程                 |
| 会议与行动项   | 主题、参会人员、议程、纪要、决定及行动项信息                           | 保存会议结论并跟进会后事项             |
| 阶段验收       | 阶段、目标、标准、结果、原因、参与人员、时间和整改关联                 | 记录成果检查及问题处理过程             |
| 扩展数据       | 附件元信息、GitHub Issue 关联信息                                      | 在相应扩展获准后关联文件与外部协作事项 |

### 7.2 数据关联与一致性

用户通过项目成员关系加入项目。一个项目包含多个需求、任务、迭代、会议和验收记录；一个需求可关联多个任务，一个迭代可安排多个任务。任务还可以关联评论、操作记录以及会议或整改来源。

系统应保证相关对象的项目归属一致，不能将其他项目的成员、需求或迭代混入当前业务。状态、角色和优先级采用限定值。移除成员后保留历史业务记录；删除项目时应处理关联数据或禁止删除，不能留下失去归属的数据。数据库结构变更应通过迁移管理。

### 7.3 主要权限矩阵

下表沿用需求基线；管理员拥有平台管理权限，其他角色在已加入的项目范围内操作。

| 操作                         | 平台管理员 | 项目负责人 | 项目成员             | 观察者 |
| ---------------------------- | ---------- | ---------- | -------------------- | ------ |
| 创建项目、修改项目基本信息   | 允许       | 允许       | 不允许               | 不允许 |
| 邀请或移除成员、修改项目角色 | 允许       | 允许       | 不允许               | 不允许 |
| 创建需求、创建任务           | 允许       | 允许       | 允许                 | 不允许 |
| 删除需求或任务               | 允许       | 允许       | 不允许               | 不允许 |
| 修改自己负责的任务           | 允许       | 允许       | 允许                 | 不允许 |
| 修改其他成员任务负责人       | 允许       | 允许       | 允许                 | 不允许 |
| 更新任务状态                 | 允许       | 允许       | 允许，须遵循审核规则 | 不允许 |
| 发布评论、创建会议           | 允许       | 允许       | 允许                 | 不允许 |
| 阶段验收                     | 允许       | 允许       | 不允许               | 不允许 |
| 查看项目数据                 | 允许       | 允许       | 允许                 | 允许   |
| 导出项目报告                 | 允许       | 允许       | 不允许               | 不允许 |

普通成员不能删除项目、移除成员或修改项目权限。任务“更新状态”的权限不代表成员可以代替负责人审核完成任务。所有受保护接口均需验证身份，所有修改操作均需在服务端检查权限，不能只依靠隐藏按钮。

## 8. 非功能需求分析

### 8.1 性能需求

| 指标                 | 需求目标                   |
| -------------------- | -------------------------- |
| 普通页面首次加载     | 不超过 3 秒                |
| 常规任务列表查询响应 | 不超过 1 秒                |
| 并发访问能力         | 至少支持 20 名用户同时访问 |
| 单项目任务规模       | 至少支持 10,000 条任务记录 |
| 图表加载反馈         | 加载过程中显示明确状态     |

上述数值沿用需求基线，属于待通过测试验证的目标。性能测试报告应同时记录设备配置、部署方式、网络条件、数据量及执行结果，以便判断测试结果的适用范围。

### 8.2 安全与隐私需求

系统应安全保存密码，对受保护接口进行身份认证，对修改操作进行服务端授权，防止越权访问、SQL 注入和路径穿越。头像及附件上传应检查文件内容或类型、大小及存储路径，并按各自需求范围实施。

JWT 密钥、GitHub Token 和数据库凭据通过环境变量提供，不写入源码、提交记录或日志。界面不能明文显示 GitHub Token，错误提示与日志不能泄露密钥、内部路径或堆栈等敏感信息。

### 8.3 易用性与异常处理需求

系统应统一显示日期、状态和优先级，主要操作支持键盘访问。空数据页面提供明确引导，删除操作二次确认，离开未保存表单时提示用户。

对于重复用户名、无效日期、无权限访问、数据不存在或请求失败，应给出可理解的提示，不能导致程序崩溃。头像取消选择或上传失败时保留原头像，避免用户因失败操作丢失已有资料。

### 8.4 兼容性与可维护性需求

系统应适用于 Windows 11 本机或局域网部署。既有技术约束为 React、TypeScript、Electron、NestJS、Prisma、SQLite 和 ECharts；GitHub REST API 仅用于相应外部关联能力，具体版本以项目锁定配置为准。

前端采用严格类型检查，后端保持控制器、服务及数据访问层的职责划分，接口提供统一响应格式与错误码，关键业务逻辑具有测试。需求、接口、数据库和页面行为应保持一致，便于后续维护和缺陷定位。

## 9. 范围边界、约束与依赖

### 9.1 首版范围

首版围绕“创建项目 → 建立需求 → 拆分任务 → 执行与审核 → 阶段验收 → 统计与导出”形成完整流程，必须覆盖 FR-01～FR-11。附件、GitHub Issue 关联、备份恢复及其他扩展按既定优先级安排，不改变核心流程的交付顺序。

### 9.2 当前不纳入的功能

- 实时多人编辑、在线聊天和视频会议。
- 移动端 App 和 AI 自动生成任务。
- GitHub 双向自动同步，以及自动创建、关闭或修改远端 Issue。
- 多组织和复杂企业权限、面向公网的大规模部署。
- 自动云备份及财务、考勤等与当前课程项目协作目标无关的功能。

### 9.3 主要约束与依赖

项目首版规划周期为 8～10 周，由三人团队承担开发或测试工作。团队应优先保证必做功能及核心流程，不因展示效果增加未经确认的能力或大型依赖。

需求和任务应以项目及成员关系为基础；任务审核依赖明确的负责人和权限规则；迭代、仪表盘及导出依赖准确的任务状态和完成数据；会议与验收需要与任务建立可追溯关系。外部 GitHub 服务是可选辅助依赖，其不可用不能阻断核心业务。

### 9.4 需求分析中的关注事项

| 关注事项                 | 对需求落实的影响                   | 处理要求                                         |
| ------------------------ | ---------------------------------- | ------------------------------------------------ |
| 角色边界不清楚           | 可能导致越权操作或合法用户无法工作 | 按权限矩阵落实界面与服务端控制，并验证项目间隔离 |
| 状态与审核含义不一致     | 统计完成情况与实际验收结果可能混淆 | 区分任务审核、需求状态和阶段验收，保留变更记录   |
| 日期与关联对象不一致     | 可能出现无效计划或跨项目数据引用   | 检查日期及项目归属，并给出明确提示               |
| 汇总数据缺少明细依据     | 可能影响课程汇报和进度判断         | 对照任务、需求及迭代明细核对统计与导出结果       |
| 建议功能占用核心交付时间 | 可能造成必做流程不完整             | 先稳定 MVP，再评估和安排建议及扩展功能           |

## 10. 验收标准与需求追溯

### 10.1 正式验收标准对应表

| 验收编号 | 用户可观察的验收要求                                                                                                                             | 对应功能需求                  |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------- |
| AC-01    | 用户注册后可登录、退出；未登录访问项目页面被拦截                                                                                                 | FR-01                         |
| AC-02    | 负责人创建项目并邀请两名成员；成员可见已加入项目，不能看到未加入项目的数据                                                                       | FR-02、FR-03                  |
| AC-03    | 创建含验收标准的需求并关联多个任务，需求详情可查看任务及完成情况                                                                                 | FR-04、FR-05                  |
| AC-04    | 成员执行任务、填写完成说明并提交审核；负责人审核通过后完成；不通过时保持待审核并显示原因；可查看完整状态记录                                     | FR-05、FR-07                  |
| AC-05    | 创建迭代并加入任务后，任务总数、已完成数、阻塞数、逾期数及完成率显示正确                                                                         | FR-06；相关统计展示关联 FR-10 |
| AC-06    | 创建会议、填写纪要并生成行动项；可设置负责人、截止日期和状态，转换为普通任务                                                                     | FR-08、FR-05                  |
| AC-07    | 阶段验收未通过时可填写原因并生成整改任务，整改完成后可再次记录验收结果                                                                           | FR-09、FR-05                  |
| AC-08    | 普通成员不能删除项目、移除成员或修改项目权限；观察者可查看但不能创建或修改业务对象                                                               | FR-03 及各模块权限控制        |
| AC-09    | 可组合负责人、状态、优先级和截止日期筛选任务，并由有权限的用户成功导出 CSV                                                                       | FR-11                         |
| AC-10    | 空项目、无效日期、重复用户名、无权限、网络失败和不存在的数据均有明确提示，程序不崩溃                                                             | FR-01～FR-11 的相关异常场景   |
| AC-11    | 有效选图后自动上传一次，头像与昵称独立保存；刷新、重新登录及其他客户端可读取；忙碌期间避免冲突，取消或失败保留原头像，错误及日志不泄露路径或堆栈 | FR-01                         |

本表为正式验收标准的对应摘要，执行测试时应同时对照需求基线中的完整条文和业务规则。FR-10 的完整仪表盘及图表范围还应逐项核对基线第 6.10 节，不能仅以 AC-05 的迭代统计或 AC-10 的异常提示代替。非功能需求按基线第 9 节验证；FR-12～FR-15 按建议或后续范围管理，本文不新增正式验收编号。

### 10.2 核心场景的验证关注点

| 场景             | 正常情况                                   | 边界情况                                           | 失败或无权限情况                                         |
| ---------------- | ------------------------------------------ | -------------------------------------------------- | -------------------------------------------------------- |
| 账号与头像       | 注册、登录、有效选图自动上传，昵称独立保存 | 取消选图、保留未保存昵称、刷新或重新登录后读取头像 | 重复用户名、会话失效、超限或实际格式不符、读取或存储失败 |
| 项目与成员       | 创建项目、邀请成员、按角色访问             | 暂停与恢复、归档只读、移除成员后历史保留           | 日期倒置、访问未加入项目、无权限修改角色                 |
| 需求与任务       | 建立需求、拆分任务、提交审核并完成         | 标题长度、项目开始日期边界、重新打开任务并填写原因 | 缺少必填信息、关联其他项目对象、成员越权审核或删除       |
| 会议与验收       | 行动项转任务、未通过后整改并再次验收       | 行动项完成或取消、保留会议及整改关联               | 无权限验收、无效输入、转换或提交失败                     |
| 统计、筛选与导出 | 统计与明细一致、组合筛选、导出 CSV         | 空项目、无匹配结果、清空筛选、较大任务规模         | 网络失败、无效日期、无权限导出                           |

上述关注点用于组织后续测试，不表示这些场景已经全部通过，也不替代最终测试记录。
