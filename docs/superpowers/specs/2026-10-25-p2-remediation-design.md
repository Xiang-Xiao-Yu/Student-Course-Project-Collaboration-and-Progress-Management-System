# P2 项目与成员缺陷修复设计

## 目标与依据

修复 PR #28 中 Issue #29 记录的负责人并发转移、项目删除审计、`null` 输入校验和成员头像响应问题，并复核 PR #30 的 P2 前端访问门禁与归档交互。范围对应 FR-02、FR-03、AC-02、AC-08、AC-10；头像兼容对应既有 FR-01、AC-11。

## 约束与非目标

- 不改变需求范围、API 路径、技术栈或依赖；不进入 P3。
- 所有状态变化与删除操作保持事务一致，权限始终由后端校验。
- 保留项目删除时现有普通 ActivityLog 的级联行为，只保证删除事件本身可留存。

## 设计决定

1. 负责人移交在事务内以旧 `ownerId` 做条件更新，并校验当前操作者和目标成员。过期移交返回明确的 409 冲突，且回滚所有变更；成功事务中只生成一条移交日志。
2. 删除审计采用独立的 `ProjectDeletionAudit` 快照表，不关联 Project/User 外键；记录项目 ID/名称/状态、操作者 ID/用户名和删除时间。一个事务先取得被删除项目快照，再删除项目并写入审计，任一步失败均回滚。
3. 输入规则采用“省略表示不更新；`null` 对可选字段无效”。简介用空字符串清空；日期不支持清空，Create/Update DTO 保持一致。审计 afterValue 与实际规范化写入值一致。
4. 成员响应复用现有 `AvatarStorageService.toDataUrl`；所有列表、邀请和角色更新共用响应映射，不返回 `uploaded:` 内部引用。
5. PR #30 的项目子路由只在当前 `projectId` 的访问检查通过后挂载；存在未保存基本信息时阻止归档并提示先保存或撤销修改。

## 删除审计方案比较

- 保留 ActivityLog：将其项目外键改为可空并使用 SetNull，可能改变所有已删除项目历史日志的保留行为。
- 独立删除快照表：只保留删除事件，维持当前其余历史日志级联语义。

采用独立快照表，变更面更窄，并能在项目和用户记录删除后保留审计主体及项目快照。

## 验收

- 同一旧负责人快照发起两个并发转移时，恰好一个成功，最终恰好一个 OWNER 且与 Project.ownerId 一致。
- 删除成功后审计记录存活；权限、确认名或审计写入失败时不产生不可追踪删除。
- Create/Update 的省略、null、空字符串、合法值、非法日期和日期范围行为明确，数据库与 ActivityLog 一致。
- 上传头像转换为可显示数据；HTTP(S)、空头像、丢失文件和项目外读取符合既有权限与回退契约。
- PR #30 不在未授权时发起子页面请求；归档不能静默锁住未保存项目资料。
